# Database design

PostgreSQL stores relational data and authorization state. Video files, thumbnails and other binaries stay in private MinIO/S3 storage. Database rows contain object keys and media metadata, never video bytes.

## Initial schema

The first Alembic revision creates:

- `users` — accounts, unique email and username, password hash and account state.
- `roles` — system roles: `user`, `moderator` and `admin`.
- `user_roles` — many-to-many role assignment with an assignment timestamp.
- `channels` — one channel per account, unique public handle, avatar/banner object keys.
- `videos` — metadata, processing status, visibility, media properties and storage object keys.
- `video_access_grants` — explicit access to private videos; one grant per user/video pair.

UUID primary keys are used for externally addressable entities. Foreign keys define deletion behavior. PostgreSQL constraints validate video status, visibility and media dimensions. Composite and feed-oriented indexes support common queries.

Passwords must be stored as Argon2 hashes generated by the authentication service. Never store plaintext passwords. Normalize email and handle values in the application before persistence.

## Migrations

Run locally from the repository root:

```powershell
python -m pip install -r backend/requirements.txt
alembic -c backend/alembic.ini upgrade head
alembic -c backend/alembic.ini current
```

Docker Compose runs the `migrate` service after PostgreSQL becomes healthy and before the API starts:

```powershell
docker compose up --build -d
docker compose run --rm migrate alembic current
```

All future schema changes must be added as new Alembic revisions. Do not call `Base.metadata.create_all()` during application startup.
