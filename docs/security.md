# Security baseline

This document distinguishes safeguards currently implemented from work still required before broad public registration.

## Implemented

- Secrets are supplied through environment variables. Production setup generates independent random values and writes `.env.production` with restrictive file permissions. Real secrets must never be committed.
- Passwords are hashed with Argon2id through pwdlib; plaintext passwords are not persisted.
- Access tokens are short-lived JWTs signed with HS256. The API validates signature, issuer, token type and expiry.
- Refresh tokens are opaque random values. PostgreSQL stores only their SHA-256 hashes.
- Refresh tokens are rotated on refresh. Reuse of a revoked token revokes the remaining active sessions in the same token family.
- The refresh token is delivered in an HttpOnly, SameSite=Lax cookie scoped to the authentication API; production enables Secure.
- Logout revokes the refresh session. Inactive users are rejected at login and refresh.
- Protected operations enforce authorization in the API. Moderation and role-management routes require the relevant roles.
- Private-video access is checked before metadata, playback or thumbnail delivery. The backend streams media from the S3-compatible object store; the current implementation does not issue presigned URLs.
- Production Compose publishes Caddy only. PostgreSQL, Redis, backend and object storage remain on the private Docker network. In development, MinIO ports are bound to localhost.
- Uploads enforce a maximum video size of 500 MiB, a maximum thumbnail size of 5 MiB, an allowlist of MIME types and basic file-signature checks. Storage keys are generated by the backend.
- Redis view-deduplication keys contain a SHA-256 digest of viewer identity rather than the raw identity. Redis failure is fail-open so auxiliary view counting does not take down the API.
- Logs must not contain passwords, access tokens, refresh tokens or storage credentials.

## Known limitations and pre-public-launch work

- **Rate limiting is not implemented.** Add request throttling for registration, login, refresh and other abuse-sensitive endpoints before opening registration broadly.
- **CSRF/origin enforcement is not implemented.** The refresh cookie uses SameSite=Lax, but this is not a substitute for an explicit origin/CSRF strategy for cookie-authenticated operations.
- Email verification, password reset and OAuth are not implemented.
- Upload validation checks declared MIME type and basic signatures; it is not a full media decode or malware scan. There is no transcoding or background media inspection.
- The anonymous view identity uses IP and User-Agent and is an MVP heuristic, not a strong identity or anti-fraud mechanism.
- The current single-node deployment is not a hardened high-availability setup. Backups, restore drills, monitoring, alerting, host firewall and routine secret/image updates remain operator responsibilities.

Do not describe the current MVP as ready for unrestricted public registration until the rate-limiting and CSRF/origin gaps have been addressed and the production deployment has been exercised end to end.
